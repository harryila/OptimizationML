# P24 CUDA executable-origin hardening

## Status and authority

P24 is frozen as a **pre-remediation-build, pre-acquisition contract**.  It
contains no CUDA repeatability, observer-noninterference, real-gradient
fidelity, shield, or training result.  The machine-readable authority is
`experiments/training/p24_cuda_executable_origin_contract.json`; the
standard-library reconstruction checks its exact bytes, its immutable P23
parent, every inherited authority, and the image-remediation source hashes.

P24 starts from the annotated
`p23-deterministic-cuda-shadow-trace-diagnostic` tag, whose target is commit
`3a1454e29edc022e92f2848e216c790d4ea8434a`.  The retained P23 outcome is an
operator-recorded pretraining stop, not a native failure manifest.  It reports
that `trace_off_a` stopped during initialized loaded-file closure after an
executable Python module appeared under writable `/tmp`.  No optimizer step,
gradient, Muon candidate, repeatability comparison, observer comparison, or
fidelity statistic was produced.  P24 therefore treats the PyTorch
generated-module route as a hypothesis that must first be reproduced with a
native, hash-bound diagnostic.

## Frozen remediation

The only intended image change is an executable-origin hardening of pinned
PyTorch `2.7.0+cu128`.  During the image build, the exact non-scriptable remote
module is generated once at

```text
/opt/p23-venv/lib/python3.12/site-packages/torch/
    _p24_generated_remote_modules/_remote_module_non_scriptable.py
```

and PyTorch's pinned instantiator is redirected to that directory.  The
contract binds three principal SHA-256 values:

- installed instantiator before transformation:
  `567d1314ee27ff0b3bd22e7c4d1157246469de25e7a3183d96debe167b193615`;
- installed instantiator after transformation:
  `1ecc8ae1ac4a517511914fff6e01c78ed3ad828bbe8a07b02079c206ee56bceb`;
  and
- generated module bytes:
  `8205b16956fb264841ecd8644784a0d157f87df79b17c16825dc1163433ce5d8`.

The supporting remote-module and template sources, byte counts, build helper,
Dockerfile, and exact P23 base-image digest are also locked.

The build helper rejects an unexpected preimage, unexpected generated bytes,
or unexpected postimage, records an image manifest, and freezes the generated
directory and file at modes `0555` and `0444`.  The patched runtime verifier
rejects an unexpected output path or content even while the image is being
built.  At acquisition time the container root is additionally read-only, so
an attempted runtime creation or alteration also fails at the filesystem
boundary.

This is not a `/tmp` exception.  Writable executable origins remain rejected;
neither `/tmp` nor `/dev/shm` is added to an allowlist.  `/tmp` retains the
P23 writable, `noexec`, `nosuid`, `nodev` tmpfs contract.  The generated source
is accepted only because it is exact image content on the read-only image
root.

## Native diagnostic

Before another gradient acquisition, P24 requires two fresh-process native
diagnostics using
`experiments/training/run_p24_executable_origin_diagnostic.py`:

1. `baseline` must reproduce the generated module under a writable `/tmp`
   origin in the old P23 image.
2. `remediated` must construct the same minimal optimizer, observe the exact
   generated bytes at the frozen image-layer path, and establish that the
   effective mount is read-only.

Each diagnostic records repository and runtime-lock bindings, the complete
contract content and source records, runtime lock, host attestation, complete
file-backed module closure, pinned source hashes, the exact generated-module
record, its effective mount, and every Boolean decision.  The diagnostic
requires caller-supplied exact hashes for the contract, runtime lock, host
attestation, repository HEAD, and repository tree, and independently checks
the P23-addendum link across the contract, source record, and runtime lock.
Its trigger is only
`import torch`, construction of one CPU FP32 parameter, and construction of an
SGD optimizer.  It performs no model or data operation, CUDA forward/backward
pass, Muon call, optimizer step, or fidelity observation.  A passing diagnostic
therefore resolves only the executable-origin issue it tests.

Every native diagnostic, including a fail-closed error record, is retained
byte-for-byte and then processed by the dedicated offline sanitizer.  The
sanitizer requires a SHA-256 independently computed from the retained native
bytes, validates the full
native schema and cross-artifact relations, retains the complete semantic
manifest, and replaces machine paths with exactly nine declared logical roots.
Its output binds both the native SHA-256 and native byte count and is published
with a no-overwrite atomic link.  The P23 acquisition artifacts continue to use
the unchanged P23 sanitizer; its schema is deliberately not reused for these
P24 diagnostic records.

## Replacement runtime and acquisition order

The P23 image, running container, runtime lock, and host attestation are not
reusable for P24 acquisition.  A new digest-selected OCI image and a new
read-only-root container must be inspected.  Fresh runtime-lock and host
attestation artifacts must be sanitized, reviewed, and committed before the
remediated diagnostic is run.  The remediated diagnostic and its sanitized,
native-byte-bound copy must then be reviewed and committed before
`trace_off_a`.  This order avoids asking a diagnostic to bind a runtime lock or
repository tree that has not yet been frozen.  The GPU, mount, network, loader,
determinism, source, data, and fresh-process contracts otherwise remain those
frozen by P23.

That evidence-only commit necessarily advances the acquisition HEAD beyond
the HEAD recorded by the remediated diagnostic.  Retain an explicit bridge
record containing both HEAD/tree pairs and the exact name-only delta.  The
delta may contain only the two sanitized diagnostic wrappers and explicit
result-binding metadata, and every frozen execution-source hash must remain
unchanged.  Do not rerun the remediated diagnostic merely to chase this
evidence commit: that would create a self-reference loop and violate the
no-favorable-rerun policy.

After both native diagnostics and the replacement runtime are frozen, the
unchanged acquisition order is:

1. `trace_off_a`;
2. `trace_off_b`;
3. exact repeatability verification;
4. `trace_on`, only after zero exact repeatability mismatches;
5. exact observer-noninterference verification; and
6. fidelity aggregation, only after both exact comparisons pass.

No numerical tolerance or `allclose` substitution is permitted.  A successful
trace-on still requires exactly `48 * 24 = 1,152` actual post-aspect BF16 CUDA
candidates, all 48 intended Muon matrices, and all 84,934,656 intended
elements.  Every P21/P22 activation, correction, cosine, amplitude, P16, P18,
and mild-intervention threshold remains unchanged.  P24 cannot be rerun until
a favorable outcome appears; the first failure is retained and routes the next
work.

## Claim boundary

This contract does not alter the P18--P21 exact or finite-precision theorems.
Even if both diagnostics and every CUDA acquisition gate later pass, the
result will be empirical evidence for one pinned stack.  It will not prove
global PL for GPT-2, stability of unrepaired upstream Muon, all-CUDA
determinism, native CUDA shield correctness, distributed parity, or training
quality and throughput parity.
